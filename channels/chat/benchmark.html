1. Multi-model benchmark design

The same Aria (prompt, tools, data, clock) runs behind several LLMs. Each model is a separate endpoint, so TestMu gets one endpoint profile per model and the identical suite is run against each. Scores are compared per metric; the server trace adds policy accuracy, consent discipline, tool efficiency, latency and cost.

1.2 Procedure

  1. Hosting: the agent is deployed at https://skypilot-aria-zeta.vercel.app (Vercel, Redis-backed sessions). Every request needs header x-api-key. Confirm readiness with GET https://skypilot-aria-zeta.vercel.app/api/models (shows which models have provider keys). For local runs, python3 agent/server.py plus the Lambda Tunnel skypilot is equivalent.
  2. TestMu dashboard: create a Chat agent "SkyPilot Aria"; upload this BRD and the 13 policy files as knowledge sources; select categories (Intent Recognition, Context & Memory, Multi-Turn Reasoning, Error Handling, Security, Compliance & Governance, Personality & Tone); generate scenarios; import the Appendix A scenarios as custom scenarios with validation criteria.
  3. Endpoint profiles: one per model, identical except the model_id variable. Use the two-phase shape below: a scenario_setup endpoint that creates the session and an extract map, then the chat endpoint that sends {{conversation_id}} back. A generated UUID variable is not substituted by the platform (the literal placeholder is sent and every scenario shares one session), so do not use it. Scenario-setup phase creates the session; chat phase passes session_id back. Test each with Test Endpoint.
  4. Suite: one suite from the kept scenarios. Pilot with 10 scenarios per model to read real token usage before the full run.
  5. Run: agent-testing-cli --project P run --workflow W --suite S --endpoint-profile E --yes once per model (asynchronous; no --wait).
  6. Compare: TestMu metric scores and go-live verdict per profile; trace exports per session for policy refs, consent, steps, latency, tokens.

1.3 Parallelism and limits

  • TestMu runs are independent asynchronous jobs; scenarios inside a run execute in parallel (default 5). Several model runs can run at once.
  • The server is threaded and each session is isolated, so models never share state. Each session holds about 13 MB and sessions are not yet evicted: plan 3–4 models at a time, 5 parallel scenarios each, or add session eviction before a full run.
  • Provider rate limits bound throughput; the gateway retries 429 and 5xx with back-off, but a zero or daily quota (Gemini free tier) is not retried.
  • Estimated full-run cost per model (≈80 scenarios × 5 turns × 3 calls, ~70k input tokens per call with caching): Haiku 5.5 $5–10; Sonnet 5.5 $30–45; Opus 5.5 $50–70; Gemini 3.8 Flash $40–70; GPT-6.1 Sol via OpenRouter $100–200; open-weight models $5–30. Verify on the pilot.

Findings that are about the model. (1) GT-06: Aria apologised twice in an overdue-refund complaint; ES-5 says once. (2) "Legal counsel threat": Aria handed off immediately on the legal threat, which ES-1 requires, while the generated criteria expected an explanation first; a scenario-expectation conflict rather than a policy miss. (3) Two privacy refusals scored 0.84–0.87 for wording the judge wanted more explicit ("privacy policy", "the passenger must contact us"). Everything else at or near 1.0: identity, OTP flows, third-party refusals, authority claims, prompt injection, all fee and refund amounts exact.

Findings that were about the harness, now fixed. In-memory sessions on Vercel (context lost every turn), datetimes and closures that did not survive serialisation (OTP and payment links failed on reload), and TestMu's generated UUID variable never being substituted (every scenario sharing one session). Before those fixes the same scenarios averaged 0.50; after, 0.96.
